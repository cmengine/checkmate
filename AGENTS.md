# AGENTS.md

## Repository Overview

Checkmate (CME) is a statically typed, embeddable scripting language implemented as a Cargo workspace in Rust (edition 2024). The implementation is early-stage: `cme-core` and `cme-compiler` contain the first real language functionality, `cme-interp` implements the tree-walking interpreter for the basic subset, and the runtime remains a placeholder.

The workspace root package is `cme`. It re-exports workspace crates behind feature flags. The intended development workflow uses `--features cli` (or the individual feature flags); the default build intentionally exposes no root APIs.

## Crates

- `crates/cme-core` — Foundation crate with no dependencies. Defines the spanned AST, source spans, and diagnostic references: primitive/inferred/void types, literals, identifiers, variable declarations, functions, calls, if/else, while, and return. Shared by compiler and future language components.
- `crates/cme-compiler` — Depends on `cme-core` and `logos`. Provides the lexer, parser, diagnostics, validator, the type checker (`check::check`, enforcing Appendix A and §2.10–§2.16 for the basic subset), the one-call `parse_source` front-end for the current subset, including functions, control flow, bare calls, newline-sensitive statement parsing, and insignificant-newline handling inside brackets, and the multi-file mod loader (`mods`, §10).
- `crates/cme-interp` — Depends only on `cme-core` (the AST is the contract; `cme-compiler` appears as a dev-dependency for the inline-source unit tests). Implements the tree-walking interpreter for the basic subset: `Value`, `InterpError`, and `Interpreter::new`/`invoke`, with overflow-checked arithmetic, truncating integer division, short-circuit `&&`/`||`, §A.6 stringification, and a fixed 1024 call-depth limit that turns runaway recursion into a clean error. The walker is the reference oracle the future bytecode VM will be differential-tested against, so its observable behavior is exact.
- `crates/cme-runtime` — Dependency-free placeholder. Currently contains starter code only; runtime services and built-ins are not implemented.
- Root package `cme` — Facade package and optional CLI. Feature-gated re-exports are: `core`, `compiler`, `interp`, and `runtime`; `cli` enables all four and provides the working lex/ast/check/run toolchain binary (`run` parses + checks first and never executes a program that produced a diagnostic). `check`, `ast`, and `run` also accept a mod directory (or a `mod.toml` path) and compile the whole §10 mod tree; `lex` and `expand` remain single-file commands.

## Whitepaper Policy

`WHITEPAPER.md` at the repository root is the language specification.

- **Read `WHITEPAPER.md` only through `mdpeek`.** This applies to every reading mechanism: shell tools, scripts, editors, search, source inspection tools, file listing with content output, and any tool or agent that can access file contents. Never use `cat`, `read`, `sed`, CodeGraph, or any other method to read it. Get `mdpeek` from `https://github.com/1matin/mdpeek.git`
- Treat the whitepaper as a human-owned language source of truth. Run `mdpeek toc FILENAME.md` to get the ToC of the file with numbers attached to them, then run `mdpeek fetch FILENAME.md [comma-seperated numbers]` to get relative bodies. Try fetching only the parts you need.
- When a task requires clarification about Checkmate language design, syntax, semantics, precedence, intended compiler behavior, or any other specification detail, **ask the user and stop** until the user answers.
- Do not infer language behavior from the whitepaper's file metadata, size, or any partial content exposure.

## Working Rules

- Always use `git` and never use `jj` commands directly. ALWAYS FOLLOW Conventional Commits SPECS FOR NAMING COMMITS!
- Keep changes focused on the affected crate and avoid implementing unspecified language behavior by guessing.
- Preserve the feature-gated structure of the root facade. Adding functionality to a workspace crate should not require enabling that crate by default in the root package.
- Lexer and parser changes must respect `cme-core` AST ownership: language data models belong in `cme-core`, while recognition/parsing remains in `cme-compiler`.
- Update lexer, parser, validator, and AST pieces together when language-facing changes require it, and add focused unit tests in the relevant crate.

## Code Review Process

- Perform code review in report-first mode: inspect the affected source and produce findings before changing code.
- For each finding, present remediation options with a recommended option first and an explicit discard option last; do not implement remediation until the user chooses.
- Keep review findings tied to concrete source locations and distinguish correctness issues from style-level changes.
- After review decisions are approved, record the accepted work in the relevant task brief or commit plan, then implement against it.
- Run `cargo fmt --check` (or `cargo fmt` when preparing changes), `cargo test --workspace`, and `cargo clippy --workspace --all-targets` as part of validation. Use the complete facade with `--features cli` when CLI-facing behavior changes.

- Build the toolchain: `cargo build --features cli`
- Run tests: `cargo test --workspace`
- Run tests with the complete facade enabled: `cargo test --workspace --features cli`
- Format: `cargo fmt`

## mdpeek

- `mdpeek toc [PATH]`: list numbered headings. Omitted `PATH` uses `WHITEPAPER.md` or the sole `.md` file.
- `mdpeek fetch PATH SECTIONS`: print selected sections, comma-separated numbers such as `1,4,23`.
- Fetch includes subsections, sorts requested sections, and exits `2` if any number is invalid.
- Always run `toc` first and use its numbers; fenced code headings are ignored.

## Repository State Notes

- The root binary reports how to build with the `cli` feature when that feature is absent.
- Newline handling is intentionally significant at statement boundaries; do not remove this behavior without explicit user direction. Newlines are insignificant only inside the innermost PARENTHESES (§A.8); inside brackets and braces they stay significant (collection elements, map entries, match arms, struct members).
- The full whitepaper language surface (structs, enums with generics, `option`/`result` and `?`, `match`, `for`-in, arrays, maps, interpolation, named arguments, `impl` blocks §10.4) parses, checks, and runs on the tree walker; `syntax.cm` at the root is its fixture (returns 0 when all internal checks pass). Impl blocks target local non-generic structs/enums or host-style dotted paths (target validation, member union, duplicate/variant-collision rejection, member bodies, and qualified/path-call resolution are checked; hosts enter through `Interpreter::invoke_member`). Implemented since: the §9 schema system (see the schema note below). Not yet implemented: the bytecode VM, AOT, `suspend` schema members and the continuation-splitting VM, and generic impl targets.
- Multi-file mods (§10) are implemented end to end in `cme_compiler::mods` plus the `import` statement. `mod.toml` (§10.2) parses through a dependency-free TOML-subset reader in `mods.rs` — name, version, `checkmate_version`, and a `[schemas]` table of namespace → target version, kept in declaration order; comments, bare/quoted keys, and single/double-quoted strings are accepted, while multiline strings, typed values, and dotted keys are rejected with line-anchored diagnostics, and every version must be `X.Y.Z`. `[schemas]` is validated for shape only: enforcing it (§9.5 capability hiding) belongs to the future schema system, as does any validation of host-rooted imports, which parse and are accepted everywhere. Discovery maps `src/**.cm` to `self`-rooted module paths (§10.3), rejects files and directories whose names are not identifier segments (they would be silently unimportable), skips dot entries, and sorts by module path so builds are deterministic. Assembly concatenates the expanded sources into one virtual program text with recorded per-module byte ranges and runs `parse_source` + `check` ONCE over it — which is what makes cross-file linking exact: duplicate top-level names collide in the shared namespace, and `impl` blocks for one target union across the mod tree with duplicate-member rejection (§10.4). `import self.a.b` resolves against the module table (a miss names the expected file at the import's span); standalone single-file builds reject self-rooted imports outright. Diagnostics stay per file through `mods::attribute_span` (spans are re-anchored to the owning module and clamped; a recovery shape that swallows "the rest of the file" — unterminated block comment, unclosed brace at EOF — may reach past its module boundary and is attributed where it starts). `cme check|ast|run <mod_dir | path/to/mod.toml>` compiles the whole tree, expanding megaprograms per module before linking; `main` stays the entry convention and may live in any module. Cross-file macro imports (a mega invoked via an imported module's name, §8.1) remain out of scope with the text-level expander. 23 unit tests live in `mods.rs`; `tests/mod_cli.rs` drives the real binary over throwaway mod trees (14 tests).
- Megaprogramming (WHITEPAPER §8) is implemented end to end at the TEXT level (plan.md's owner mandate: the pass emits Checkmate source, not AST, so `cme expand` can write it out). The subsystem lives in `crates/cme-compiler/src/mega/` (`scan.rs` region/mega/grammar detection with islands + heredocs, `profile.rs` lexical profiles and balance, `pattern.rs`/`matcher.rs` the §8.3 packrat engine with parse-integrated extents and validators, `template.rs` §8.4 elaboration, `ctxexpr.rs` `where` conditions, `cteval.rs` the §8.5 compile-time evaluator running the file's own pure functions on the real interpreter); data models are in `crates/cme-core/src/mega.rs`. `cme expand <file.cm>` (root CLI, `cli` feature) writes `<stem>_expanded.cm` side by side with the original; `cme expand --provenance` annotates each root mega site with `// @ name! src:line:col` (default output stays byte-deterministic). Grammars support `extends` (rule override/inherit, lexical profile inheritance) and profile static checks (line-mode machinery rejected in flow grammars and inside `soft`). The pattern language additionally covers the §8.1/§8.3.10 inert editor annotations (`#complete`/`#hover`/`#token`), §8.1 INLINE entry patterns (`mega name(pattern…) { … }` without a leading rule reference; top-level binds seed the template directly), §8.3.3 pure-function fragment validators and the parameterized `$tt<"open" "close">`, the §8.3.4 `.span` accessor and the native `append(list, item)` core-library stand-in used for context accumulation (`some … in` short-circuits per §A.5), the §8.4 `[each … where cond { … }]` filter and `$"…"` interpolation in value positions, and the §8.5 `cm.code.fn` builder; §8.1's declare-before-invoke rule is a static check on the original source (template-authored invocations are exempt). `mega.cm` at the repo root is the §8.8-shaped fixture: HTML, CSS, JS, TS (via `grammar ts extends js`), Python, JSON, YAML (anchors/aliases/`<<` merge), TOML (datetimes + the `@tablesConsistent` require), SQL, and RE megaprograms plus the inline/`$template`/`$tt`/type-position/heredoc demos, all expanding, type-checking, and running (`cme run mega.cm` exits 0, 21 invocations).
- Block comments end at the first `*/`; an unterminated block comment swallows the rest of the file (one clean lex error).
- Host embedding APIs (WHITEPAPER §13) are implemented over the shipped front end and tree walker. `crates/cme-api` is the Rust API: `Engine::new` / `load_source` / `load_file` / `load_mod` apply the exact CLI gate (megaprogram expansion when `mega::expand::mentions_megaprogram` fires, `parse_source`, the §10 standalone-import check, `check`) so a program with any diagnostic never becomes invocable; `CompiledProgram` is immutable Send+Sync exposing `entry_points`/`interface_targets`/`manifest`/`modules`; `Context::invoke`/`invoke_member` run each invocation with a fresh fuel cell and deadline under cloned `ExecutionLimits` (§5.5 fuel / deadline_ms / max_call_depth, 0-or-None = unset), which makes contexts Send+Sync and concurrent invocations race-free. `ExecutionError` carries a kind (Runtime/Budget/Deadline/CallDepth/UnknownEntry) plus re-anchored file/line/column for mod builds via `mods::attribute_span` — hosts never see virtual-text coordinates. Schema-driven §13.1 surfaces (`register_capability`, generated proxies, async futures, `.cma` artifacts) wait for the schema system and bytecode VM. The facade re-exports `Engine`, `ExecutionLimits`, `CompiledProgram`, `Context`, `Value`, `MAX_CALL_DEPTH` flat behind the `api` feature (and as `cme::api`); a dev-dependency cycle in cme-api pins that shape from a consumer's view. The interpreter gained the host-facing controls underneath: `with_call_depth_limit` (0 and ≥ MAX_CALL_DEPTH keep the default), `with_deadline` (checked at the same safepoints as fuel), `InterpError::kind()` (fuel message lost its "compile-time" prefix since the meter now serves host runs too), and `Value` `From`/`as_*` conversions.
- The §9 schema system is implemented end to end. `cme-core/src/schema.rs` owns the data model (Version, SchemaMember, SchemaContract, SchemaFile, SchemaStruct/Enum, requires-path qualification, PascalCase/camelCase helpers); `cme-compiler/src/schema.rs` parses `.cm` schema files with a dedicated scanner (versions are `X.Y.Z` and scan as one token — the schema header takes the same unprefixed shape as `since` tags and manifest targets, and the retired `v1.4.0` spelling reports one migration diagnostic; comments and newline-delimited layout supported; both §9.1 `requires` spellings accepted: after the name or first inside the body) and builds `SchemaSet`/`SchemaContext` (one namespace per file, boundary type names unique across namespaces since the script type space is flat, every `requires` resolving to a real interface; `grant_all` for loose sources, `grant_targets` for a mod manifest's `[schemas]` — unlisted namespaces invisible, no target may exceed the schema's own version). The set build also rejects a member tagged `since` beyond its own schema's version (it could never be visible — a forgotten version bump, §9.5), and the parser rejects `optional` on CAPABILITY members (§9.5 defines the flag for interface members a mod may skip; a host-provided capability member must always exist). Capability/interface NAMES are case-free (every whitepaper path is camelCase) while schema-declared TYPES and members are PascalCase-enforced; `suspend` members parse and are rejected with a pointed diagnostic (the §4 async system stays out of scope). `check_with_schema` enforces the contract at compile time: §9.3 boundary types join the type registry first, §2.5 top-level capitalization, import/capability-call gating (import prefix, `requires` all three gates — the interface-impl rule, the capability-IMPORT gate (the §9.4 "cannot import or call"), and the capability-call gate, exact member signatures, declared return types), §9.5 version hiding (calls AND impls), §10.4 completeness/exactness (optional members skippable, param names free). An impl target naming an UNGRANTED or UNKNOWN namespace is an error rather than a silent skip (an impl is not an import: impl-only programs must be validated too, and silently skipping would ship an interface the schema never checked; the §9.4 rule-1 diagnostic anchors at the impl site, not the schema's requires span). `cme-interp` gained the engine-agnostic `CapabilityHost` seam (by-value args, host errors as span-anchored runtime errors) plus `with_declarations` for schema types; the megaprogram evaluator never attaches a capability host, so §8.5 purity holds by construction. `cme-api`'s Engine holds schemas + providers (`register_schema`/`load_schema_text`/`load_schema_file`, `register_capability` with path-shape validation; Engine is Clone, no longer Copy) and gates loads: schema-aware checking plus a load-time provider-presence check (a call the host cannot dispatch is a load failure); contexts snapshot providers and dispatch through the seam; `CompiledProgram` carries schema types synthesized as AST declarations (`cme_compiler::schema::declaration_statements`) fed via `with_declarations`. Context invocations enforce the §5.7 reentrancy prohibition: a thread-local active-context guard (keyed on a shared identity, so a CLONE is the same logical context) rejects a capability's nested `invoke`/`invoke_member` on the same context with a new `ErrorKind::Reentrant` — the outer invocation survives, other contexts and threads stay free; cme-ffi maps the kind to `CM_ERROR_INVALID_ARG` and the C host exercises the whole shape (9 checks). `cme-schema-macro` (feature `schema-macro`) generates compile-time-verified Rust bindings from the real schema file: capability traits (host impl = compile-time signature verification), CapabilityProvider bridges, typed interface proxies (result<T,E> keeps the script's Err payload as a value; construction fails with an UnknownEntry error on unimplemented interfaces — through `Proxy::new(&context)` AND through `Context::get_interface::<P>()`, the WHITEPAPER §13.1 shape, via the `InterfaceProxy` trait the macro implements for every proxy; the facade flat-re-exports it), and the runtime SchemaFile descriptor. `schema::codegen_c` emits the C header: per-member function-pointer typedefs + vtable + `CME_<NS>_<CAP>_REGISTER` macro whose `_Static_assert(_Generic(...))` lines verify every host implementation's signature at COMPILE time (missing member = preprocessor error), exact-arity interface invocation helpers, and struct/enum pack/unpack helpers (by-name fields; every `_pack` takes the host value BY ADDRESS so nested schema types compose recursively; `str` fields unpack to OWNED `char*` copies freed with `cm_string_free`; enums are real tagged unions with per-variant payload structs dispatched through `cm_value_enum_variant`, payload-count-checked, leak-free; container shapes ride the cm_value accessors). The header is multi-include-safe (`cme_future_take_sync` under `CME_SCHEMA_GEN_FUTURE_TAKE_SYNC`), byte-deterministic (CLI-tested), and compile-verified in tests both positively (a schema-conforming consumer compiles) and negatively (a wrong-signature provider and a missing member each fail the build). The CLI grew `--schema` (repeatable) for check/ast/run, `cme schema` (validate one file), and `cme codegen-c` (emit the header); mod runs narrow the grant through the manifest; diagnostic rendering names the RESOLVED file argument (the `--schema` pairs are consumed first, so `cme check --schema s.cm x.cm` renders `x.cm:…`, never the literal `--schema`). cme-ffi gained `cm_schema_parse|parse_file|destroy`, `cm_engine_register_schema`, and `cm_engine_register_capability` (providers dispatch to C function pointers over the borrowed-args/owned-result convention), and apps/c_host walks the full C flow (246 checks) INCLUDING the generated header consumed for real: cme-ffi's build script generates `chost_schema_gen.h` from apps/c_host/engine.cm (a schema defect fails the build) and compiles main.c with `CME_HOST_HAS_SCHEMA_GEN`, whose guarded section registers providers through the `CME_CHOST_GRAPHICS_REGISTER` macro (compile-time signature verification), unpacks script struct values through the typed layer, calls the script's interface through the exact-arity helper carrying a schema enum with a payload, and round-trips the enum and a script-built struct through the generated pack/unpack; the Makefile generates the header as a hard prerequisite. apps/rust_host consumes the Rust half end to end: `cme_schema_bindings!(path = "schemas/game.cm", crate = ::cme::api)` generates bindings from the app's own schema at app compile time, `WindowService` implements the generated trait (compile-time verification of the app itself), `run_schema_demo`/`--schema-demo` walks descriptor → provider → schema-gated program → `get_interface` proxy calls (an `Event::Scored` payload crosses to the script and back), and `--schema <file.cm>` registers runtime contracts; cross-namespace `requires` (§9.2/§9.4), version-aware prerequisite completeness (§9.5 hidden members), interpreter-vs-context seam parity, and mod-based provider dispatch are pinned by tests.
- `crates/cme-ffi` is the stable C ABI (§13.2): `include/cme.h` defines the full contract (ownership, lifetimes, threads, fill conventions) and `src/lib.rs` implements it over cme-api — `cm_engine_t`/`cm_program_t`/`cm_context_t`/`cm_future_t`/`cm_value_t` opaque handles with NULL-tolerant destroys, `cm_engine_load_source|load_file|load_mod(engine, …, cm_error_t* out)` that ALWAYS writes the report (kind COMPILE/IO/INVALID_ARG with rendered `path:line:column` messages; success fills kind NONE + empty strings), `cm_invoke(ctx, target, member, args, argc)` with BORROWED arguments (NULL/empty target routes to plain functions; NULL future only for host misuse), the `cm_future_poll/take_value/get_error/destroy` set (synchronous resolution means READY or ERROR on first poll; CM_PENDING is reserved for the continuation-splitting VM; error reports are fresh owned copies per call), and value constructors/builders/accessors with kind-checked `cm_status_t` results. Strings handed to C are OWNED copies freed with `cm_string_free` — Rust `String` is not NUL-terminated, so borrowing `as_ptr()` would read past the end from C (a real bug this API caught); embedded NULs render as U+FFFD. Engine handles are real freeable addresses, not zero-sized dangling pointers (regression-pinned). `apps/c_host/main.c` is the C consumer: 208 self-checking assertions over the entire ABI including all three §5.5 limits and misuse shapes; its Makefile builds standalone against `libcme_ffi.a`, and cme-ffi's build script compiles the SAME file (with `CME_HOST_EMBEDDED`) into `cargo test`, so the workspace run exercises the real C client in-process. `apps/rust_host` is the Rust consumer: a `cme-rust-host` CLI (lib+bin) that loads file/mod/mod.toml, applies `--fuel/--deadline-ms/--depth` flags, invokes `entry` or `target.member` (split on the LAST dot), prints CMON results, and exits 0/1/2/3/4 for success/execution/compile/usage/IO — with its logic in a testable lib (20 integration tests).
- `crates/cme-lsp` is the language server (`cme lsp`, stdio, salsa-incremental). The workspace is auto-detected: `workspace::Workspace` walks up from a document to the nearest `mod.toml` (§10.1), collects schema candidates under the mod root (excluding `src/`) plus the parent directory's `schemas/` tree — the layout this repo's host fixtures use — and grants them through the manifest's `[schemas]` table exactly like a CLI mod run (§9.5/§10.2; no `[schemas]` table → every discovered namespace, for loose host-style projects). Results cache by mtimes plus open-buffer texts, so an UNSAVED schema buffer drives the contract scripts see; a schema file with parse diagnostics falls back to its last clean parse (a mid-edit broken schema never darkens every script; its own buffer reports the defect). `workspace::ModPlan` runs the CLI's mod pipeline (load with open-buffer overrides, per-module mega expansion, §10 assembly, `check_with_schema`) and re-anchors diagnostics per module via `mods::attribute_span`, so cross-module calls, self-import validation, and §10.4 impl unions report inside the editor. Script features are schema-aware: §9.3 boundary types complete and hover (kept OUT of document symbols and go-to-definition — they live in the schema file), `namespace.capability.member` host paths resolve through `Analysis::host_path`, completion offers contract members, named arguments in capability calls, schema import segments, `self.` module segments from the module table, and signature-exact fills for missing `impl <namespace>.<interface>` members (§9.1/§10.4). Schema FILES got their own authoring surface (`features::schema_docs` over the parser's public `schema_tokens`): top-level/contract/type completion contexts (`optional` only in interfaces per §9.5, `void` return-position only), hover for the header, every declaration, and member signatures, and a document outline. Mega files get §8 completion (`features::mega_completion` over `mega::scan_mega`): top level offers `mega`/`grammar`, pattern position offers the fragments/combinators/annotations, template position the §8.4 constructs, grammar bodies the profile declarations switching to the pattern language inside `rule` bodies, and invocation regions (plus heredocs) stay silent — foreign text. Position features still decline for mega files whose spans live in expanded-text coordinates; completion is safe because `scan_mega` works in the user's own coordinates. Suites: `schema_mod_suite.rs` (34 wire tests over throwaway mod trees), `schema_file_suite.rs` (24), `mega_completion_suite.rs` (19), plus the wire/convert/resolution/tokens suites.
